## 6. 실행 절차와 명령 틀

아래 명령은 현재 CLI 기준의 틀이다. 대문자 경로는 확인된 실제 배치로 교체한다. `.venv`, 로컬 설정, 자격, 서비스가 새 세션에도 존재한다고 가정하지 않는다. 실행 전 최신 `--help`와 README를 대조한다.

1. Git 상태·지침·인계 자료를 읽고 위 표와 미완료 연결을 확인한다.
2. 필요한 연결 보완·검증을 완료하고 측정 기준과 환경을 기록한다.
3. 현재 코드와 일치하는 모델별 `check --final` 근거를 확인하거나 다시 확보한다. A가 별도 수집기를 쓰면 README의 `--collect-command`도 필요하다.
4. A·B1 T1, T2, T3를 구분해 수행한다. 필요한 B2 선행 근거를 보존한다.
5. B2가 준비되고 최종 검증까지 통과하면 T4를 수행한다. B1 비교 조건이 유지됐는지 확인한다.
6. 원본 기반 report 재생성·수치 대조 후 결과를 해석한다.

```sh
.venv/bin/python tests/conformance/runner.py experiment --suite T1 \
  --config tests/conformance/config.a.local.json tests/conformance/config.b1.local.json \
  --observer-auth bearer \
  --validation-batch results/ACTUAL_A_FINAL_BATCH \
  --validation-batch results/ACTUAL_B1_FINAL_BATCH
```

T2·T3는 위 명령의 `--suite`만 각각 바꾸되, 실제 수집 연결과 현재 검증 배치의 유효성을 먼저 확인한다. 반복 수를 낮추거나 실패 시도를 보충하는 옵션을 추가하지 않는다.

```sh
.venv/bin/python tests/conformance/runner.py experiment --suite T4 \
  --config tests/conformance/config.b2.local.json --observer-auth bearer \
  --validation-batch results/ACTUAL_B2_FINAL_BATCH \
  --prerequisite-batch results/ACTUAL_A_FINAL_BATCH \
  --prerequisite-batch results/ACTUAL_B1_FINAL_BATCH \
  --prerequisite-batch results/ACTUAL_AB1_T1_BATCH

.venv/bin/python tests/conformance/runner.py report --batch results/ACTUAL_EXPERIMENT_BATCH
```

B2의 `check --final`에도 A·B1 최종 검증 및 T1 계측 배치를 `--prerequisite-batch`로 전달해야 한다. B2를 A·B1의 T2/T3 명령에 섞지 않는다. B2 T1 선택은 실행기에서 T4로 구분된다.

## 7. 반복·계산·통계 규칙

계측 명세가 원문이다. 아래는 실행 전 대조할 요약이다.

- T1: 모델별 워밍업 3회 + 본 시도 30회. 실패를 빼고 성공 30회까지 채우지 않는다. 여러 모델은 반복마다 순서를 교대하고 실제 순서를 남긴다.
- T2: AC-08/09/10 각각 10회. T3: AC-11 5회. B2 T4: 워밍업 3회 + 본 시도 30회에서 정상 흐름·재할당을 함께 수집한다.
- readiness 조회는 이전 응답 후 10ms, 결과 조회는 50ms, 개별 HTTP 한도 5초, T3 첫 Y 응답 추가 지연 10초, 복구 재제출 최소 간격 1초·추가 최대 3회, 본문 최종 관측 한도 60초다. 변경은 승인 후 모든 영향 비교에 적용한다.
- 주 지표는 같은 공통 관측기의 단조 시계로 계산한다. 내부 확정·로컬 반영·최초 확정 관측·후속 readiness를 구분하고 다른 프로세스의 단조 시각을 빼지 않는다.
- `T_A`는 X→Y와 Y→Z의 확정 관측 후 readiness 관측까지의 합, `T_C`는 Y/Z 최초 제출부터 최초 확정 관측까지의 합, `T_W`는 readiness부터 최초 제출까지의 합이다. 실행별 `T_E = T_A + T_W + T_C`를 확인한다.
- 유효한 정상 성공 표본의 n/P50/P95/min/max와 전체 시도·성공·거부·미완료·계측 무효 건수를 함께 보고한다. nearest-rank `ceil(p*n)`을 쓰고 실행별 합계를 먼저 구한다. 구간별 P95를 더하지 않는다.
- 표본이 없으면 null이다. 미완료를 0ms나 관측 한도로 채우지 않고, 느리다는 이유로 제외하지 않는다. 워밍업·실패·제외 사유와 run_id를 보존한다.
- T3는 실제 첫 응답 보류·해제·내부 확정·단일 효과를 확인한다. 복구 시간에는 주입·조회 비용이 포함된다. 성공 후 멱등성 확인 재전송과 복구 재시도를 구분한다.
- B2는 계약별 재할당·사용 불가 구간, 실제 성공 계약 수, API/배치/재시도 수를 구분한다. 필요한 계약 전체의 준비 구간을 개별 시간 합으로 대신하지 않으며 E2E에 재할당 시간을 중복 가산하지 않는다.

## 8. 보존할 결과물과 해석 방식

- 배치별 manifest/events/checks, run별 입력·응답·snapshot·원본 구현 로그, `runs.csv`, `summary.csv`, `reassignment.csv`, `complexity.csv`, `report-provenance.json`, `report.md`, `figures/`의 PNG·SVG를 보존한다. 실제 출력 파일은 report 코드와 대조한다.
- `report`는 원본을 바꾸거나 모델을 재실행하지 않고 파생 파일을 재생성한다. 원본 해시 검증과 대표 실행의 계산값·집계값을 대조한다. 다른 배치를 합치는 비교표·그래프가 필요하면 기존 report 기능을 확인하고 최소 범위로 작성하며 입력 배치·필터·계산 근거를 남긴다.
- 그래프는 A vs B1의 정상 시간 분포·P50/P95, T2 정합성·이중 사용 증거, T3 복구 시간·조회·재시도·미완료, B1 vs B2 추가 재할당 비용을 구분한다. 정상·경합·장애 값을 한 분포로 섞지 않는다.
- 연결 복잡성은 인터페이스·기존 변경 단위·업무 메시지·예외 경로의 근거 목록을 검토한다. 자동 집계나 변경 줄 수로 우열을 단정하지 않고 네 항목을 하나의 임의 총점으로 합치지 않는다. 미수집 Canton 내부 프로토콜 메시지는 미계측으로 표시한다.
- 관측된 사실, 그 원인에 대한 추정, 미확인 항목을 구분한다. 차이가 관측·폴링·구현·환경·재할당 중 어디에서 발생했는지 증거로 설명한다. 증거 없이는 원인을 단정하지 않는다.
- 국채 전체 묶음·자동 제출·로컬 PoC 조건의 결과다. 사람의 승인·협상 시간, 실제 결제 완결성, 운영 금융시장·Global Synchronizer의 성능이나 블록체인의 일반적 우월성으로 확대하지 않는다. 30회 P95는 탐색적 관측이며 운영 SLA 추정이 아니다.
- 대용량 원본의 보관·공유 접근과 비밀값 제외를 확인한다. 결과의 Git 포함·외부 업로드는 별도 사용자 결정이며 자동 실행하지 않는다.
