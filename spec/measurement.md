# 공통 계측 명세 — 기관 간 담보 이동성 비교 PoC

상태: 연구 총괄이 검토·승인한 계측 명세. 세부 JSON Schema·fixture와 실행 환경 검증은 후속 작업이며, 현재는 아직 spec-v1.0이 아니다.

## 1. 목적과 측정 원칙

A·B1·B2에 동일한 업무 입력·관측 기준·부하·자동 제출 조건을 적용한다. B2 개발·기능 인수는 business.md와 acceptance.md의 조건에 따라 진행한다. B2 비교 실험(T4)은 A·B1 최종 검증·선행 T1 계측과 B2 최종 검증을 확보한 뒤 수행한다. 조기 개발은 동일 조건·필수 반복·원본 증빙 요건을 완화하지 않는다.

핵심 비교는 A vs B1이다. B1 vs B2에서는 재할당에 따른 추가 비용을 분리한다.

다음 원칙을 유지한다.

- 거래 접수, 최종 확정, 로컬 반영, 후속 사용 가능을 구분한다.
- 같은 묶음·거래 흐름의 이벤트만 연결하여 계산한다.
- 사람의 승인·협상 시간을 제외하고 준비 완료 후 자동 제출한다.
- 자동 제출 대기시간도 실제로 측정한다.
- 정상·경합·장애 실행을 별도 집계한다.
- 실패·미완료 실행을 정상 성공 표본에서 조용히 제외하지 않는다.
- 로컬 결과를 실제 금융시장·Global Synchronizer 성능으로 일반화하지 않는다.

## 2. 공통 관측기와 시계

### 2.1 주 지표의 시계

주요 시간 지표는 같은 실험 실행기·관측기의 단조 시계로 계산한다.

관측기는 다음 시점을 기록한다.

- 명령 전송 직전
- 확정 결과를 처음 확인한 직후
- 유효한 readiness 응답을 처음 확인한 직후
- 타임아웃·재시도·복구 완료를 확인한 시점

단조 시계의 값은 나노초 정수 문자열로 저장하고 결과표에서는 밀리초로 변환한다.

벽시계 UTC 시각은 로그 대조용으로 함께 남길 수 있지만, 기간 계산에 우선 사용하지 않는다.

다른 프로세스의 단조 시계 값을 직접 빼지 않는다. 각 이벤트에는 시계 식별자를 기록한다.

### 2.2 확정 관측과 내부 확정

주 지표의 `commit`은 공통 관측기가 해당 요청의 유효한 최종 확정 결과를 처음 수신한 시점이다.

- POST 응답이 COMMITTED이면 그 수신 시점이다.
- 먼저 PENDING·UNKNOWN을 관측했다면 결과 조회 등으로 COMMITTED를 처음 확인한 시점이다.
- 접수 응답이나 추측한 상태는 확정으로 인정하지 않는다.
- 나중에 도착한 중복 응답으로 최초 관측 시각을 바꾸지 않는다.

시스템 내부에서 실제 확정된 시각은 별도 보조 이벤트로 기록한다.

따라서 주 지표에는 결과 전달·조회에 따른 관측 지연이 포함된다. 이를 내부 DB·Canton 프로토콜의 순수 처리시간이라고 부르지 않는다.

서로 다른 시계의 내부 확정 시각과 관측 시각을 빼서 전달 지연을 계산하지 않는다. 동일 시계로 확보한 구간만 보조 수치로 사용한다.

### 2.3 준비 완료 관측

`ready`는 후속 플랫폼의 유효한 readiness 응답에서 처음 `ready=true`를 확인한 시점이다.

단순한 로컬 반영, 선행 플랫폼의 성공 응답 또는 HTTP 접속 성공으로 대신하지 않는다.

주요 정상 경로에서는 선행 확정을 확인한 즉시 후속 readiness 확인을 시작한다.

readiness가 관측되면 추가 업무 검토나 사람이 정한 대기를 넣지 않고 다음 명령을 제출한다.

조회 주기 때문에 실제 사용 가능 시점보다 늦게 관측될 수 있다. 조회 조건과 실제 호출 간격을 함께 기록한다.

## 3. 공통 실행 설정 — 초기 기준

| 항목 | 초기 값 |
|---|---:|
| T1 워밍업 | 모델별 3회 |
| T1 본 측정 | 모델별 30회 |
| AC-08·09·10 경합 실행 | 케이스별 10회 |
| T3 응답 지연·복구 | 모델별 5회 |
| B2 정상·재할당 측정 | 정상 실행 30회에서 함께 수집 |
| readiness 조회 간격 | 이전 응답 수신 후 10ms |
| 진행 중 요청 결과 조회 간격 | 이전 응답 수신 후 50ms |
| 개별 HTTP 호출 응답 대기 한도 | 5,000ms |
| T3 최초 제출 응답의 추가 지연 | 10,000ms |
| 복구 중 명령 재제출 간격 | 이전 재제출 시작 후 최소 1,000ms |
| 복구 중 추가 명령 재제출 상한 | 원래 요청당 3회 |
| 최종 관측 한도 | 테스트 본문 시작 후 60,000ms |

추가 설명:

- readiness·결과 조회는 같은 조회를 겹쳐 보내지 않는다.
- 즉시 확정 결과를 받은 정상 요청에는 결과 조회를 추가하지 않는다.
- 조회와 명령 재제출을 구분한다.
- AC-11에서 성공 확인 후 수행하는 멱등성 확인용 재전송 1회는 복구 재시도와 별도로 기록한다.
- 정상 부하는 한 번에 하나의 거래 흐름이다. T2에서만 두 호출을 공통 시작 장벽으로 시작한다.
- 워밍업은 새로운 실행 데이터로 수행하고 통계에서 구분한다. 워밍업 실패를 숨기지 않는다.

이 값은 실제 환경에서 적합성이 검증된 성능 수치가 아니라 최초 공통 설정이다.

사전 실행에서 정상 거래 자체가 타임아웃을 자주 넘는다면 원인을 확인하고 연구 총괄 승인 후 모든 모델의 공통 설정을 변경한다. 일부 모델의 설정만 조정하지 않는다.

설정은 본 측정 전에 고정하고, 변경하면 영향을 받는 비교 전체를 다시 수행한다.

## 4. 공통 이벤트와 로그

### 4.1 최소 이벤트

| 이벤트 | 의미 |
|---|---|
| `COMMAND_SUBMITTED` | 해당 호출을 전송하기 직전 |
| `COMMIT_OBSERVED` | 원래 논리 요청의 확정 성공을 처음 확인 |
| `REJECTION_OBSERVED` | 확정 거부 확인 |
| `LOCAL_APPLIED` | 해당 DB·Participant에서 관련 상태 반영 확인 |
| `READY_OBSERVED` | 후속 readiness가 참임을 처음 확인 |
| `CALL_TIMEOUT` | 호출 응답 대기 한도 초과 |
| `RESULT_CHECKED` | 원래 요청의 결과 재확인 |
| `COMMAND_RETRIED` | 복구 목적의 동일 명령 재제출 |
| `FAULT_ACTIVATED` | 응답 지연 장치 활성화 |
| `RESPONSE_HELD` | 지연 대상 응답을 보류하기 시작 |
| `FAULT_RELEASED` | 응답 보류 해제 |
| `RECOVERY_COMPLETED` | 최종 결과와 업무 상태의 정합성을 확인 |
| `RUN_FINISHED` | 실행 종료와 최종 판정 |

내부 확정, 권리 생성·소진·잠금, 실제 API·이벤트·원장 호출 및 B2 재할당 이벤트도 모델별 로그로 남긴다.

### 4.2 로그 필드

각 이벤트는 해당되는 식별자를 포함한다.

- 이벤트 ID·이벤트 종류
- 모델·테스트 ID·실행 ID
- 요청 ID·호출 시도 ID
- 묶음 ID·거래 ID·관련 계약 참조
- 플랫폼·행위 주체
- 생산 프로세스·시계 ID·이벤트 순번
- 단조 시각·선택적인 UTC 시각
- 요청 결과·오류 코드
- 전후 업무 버전
- B2의 계약·재할당 ID·source·target
- 설정·fixture·코드 버전 참조

관측기 수신 시각과 생산 프로세스 내부 발생 시각을 별도 필드로 구분한다.

원래 요청 ID는 재시도에도 유지하고, 물리적 호출마다 다른 시도 ID를 부여한다.

로그는 구조화된 JSONL로 저장한다. 실제 필드명과 Schema는 후속 공통 스키마에서 고정한다.

토큰·비밀값은 기록하지 않는다.

## 5. ①~③ 시간 지표

다음 이벤트는 모두 동일 실행·묶음의 정상 X→Y→Z 흐름에 속한다.

| 기호 | 관측 시점 |
|---|---|
| `t_X_commit` | X Repo 확정 결과 최초 확인 |
| `t_Y_ready` | Y 증권대차 준비 완료 최초 확인 |
| `t_Y_submit` | Y의 최초 논리 요청 전송 직전 |
| `t_Y_commit` | 원래 Y 요청의 확정 결과 최초 확인 |
| `t_Z_ready` | Z CCP 배정 준비 완료 최초 확인 |
| `t_Z_submit` | Z의 최초 논리 요청 전송 직전 |
| `t_Z_commit` | 원래 Z 요청의 확정 결과 최초 확인 |

재시도는 새로운 `t_Y_submit`이나 `t_Z_submit`으로 시작점을 바꾸지 않는다.

### 5.1 Availability Latency

```text
T_A_XY = t_Y_ready - t_X_commit
T_A_YZ = t_Z_ready - t_Y_commit
T_A    = T_A_XY + T_A_YZ
```

### 5.2 Completion Latency

```text
T_C_Y = t_Y_commit - t_Y_submit
T_C_Z = t_Z_commit - t_Z_submit
T_C   = T_C_Y + T_C_Z
```

### 5.3 Waiting과 End-to-End Latency

```text
T_W_Y = t_Y_submit - t_Y_ready
T_W_Z = t_Z_submit - t_Z_ready
T_W   = T_W_Y + T_W_Z
T_E   = t_Z_commit - t_X_commit
T_E   = T_A + T_W + T_C
```

## 6. ④ 상태 일관성·이중 배정

### 6.1 호출과 논리 요청 집계

- `N_success`: 최종 확정 성공한 고유 논리 요청 수
- `N_reject`: 최종 확정 거부된 고유 논리 요청 수
- `N_pending`: 최종 관측 한도까지 결과가 확정되지 않은 고유 논리 요청 수

전체 호출 수·중복 응답 수·조회 수는 별도 기록한다.

동일 요청 재전송 3회가 같은 성공을 반환해도 성공은 한 건이다. 의도된 경합 거부는 시스템 장애 건수와 구분한다.

### 6.2 이중 배정

`N_double`은 동일 묶음에 대해 상충하는 유효 사용 권리 또는 중복 배정이 확인된 고유 사례 수다.

집계 단위는 실행·묶음·위반 유형·관련 거래 집합으로 식별한다. 같은 위반의 반복 조회나 복제본을 여러 건으로 세지 않는다.

다음을 함께 보고한다.

- 위반이 발생한 실행 수 / 검증 가능한 실행 수
- 고유 위반 사례와 관련 요청·거래
- 상충하는 사용 권리와 CCP 중복 배정의 유형별 내역
- 최종 상태뿐 아니라 확정·소진·잠금 이력
- 검증 불가능하거나 증빙이 누락된 실행 수

거부가 정상이라는 이유만으로 모든 중간 상태가 안전했다고 가정하지 않는다. 관측 범위가 제한되면 그 한계를 명시한다.

## 7. ⑤ 장애 복구 비용

### 7.1 시간 정의

```text
T_R = t_recovered - t_failure
```

- `t_failure`: 공통 관측기가 응답 지연 장치를 활성화하고 이를 확인한 시점. Y 최초 제출 직전에 기록한다.
- `t_recovered`: 원래 Y 요청의 확정 결과와 S2의 업무 정합성을 확인한 시점.
- 타임아웃 시점은 장애 감지 시각으로 별도 기록한다.
- 보류된 응답이 뒤늦게 도착한 시점을 복구 완료로 대신하지 않는다.
- Z까지 진행한 최종 성공 시간과 Y 복구 시간을 구분한다.

보조 구간:

```text
장애 감지시간 = t_timeout - t_failure
감지 후 복구시간 = t_recovered - t_timeout
```

이 정의의 `T_R`에는 Y 거래 처리와 응답 대기·재확인 시간이 포함된다. 순수한 시스템 수리시간으로 해석하지 않는다.

### 7.2 호출과 미완료 집계

- `N_retry`: UNKNOWN 이후 복구 목적의 추가 명령 제출 수
- `N_query`: 원래 결과를 확인한 조회 수
- `N_pending`: 관측 한도까지 최종 결과를 확인하지 못한 논리 요청 수
- 성공 후 멱등성 확인용 재전송 수: 별도 집계

실제 복구가 결과 조회만으로 끝나면 `N_retry=0`이 정상이다.

모델 내부의 추가 재시도·조정 작업은 외부 호출과 구분하여 별도로 기록한다.

### 7.3 T3 장애 주입 검증

- 원래 Y 제출의 첫 응답에만 공통 추가 지연을 적용한다.
- 복구 조회와 후속 재전송은 같은 장애로 계속 차단하지 않는다.
- 업무 처리와 내부 확정을 중단하거나 권리를 직접 변경하지 않는다.
- 실제 응답 보류 시작·해제·보류 시간을 기록한다.
- 지연 없는 정상 실행에서 같은 타임아웃이 반복된다면 설정·환경을 먼저 점검한다.
- 의도한 지연이 적용되지 않았거나 원래 처리 지연과 구분할 증거가 부족하면 유효한 T3 주입 결과로 집계하지 않는다.

주입 자체의 고정 지연이 포함되므로 T3 총시간만으로 모델의 본래 처리 성능을 판단하지 않는다.

## 8. ⑥ 플랫폼 연결 복잡성

X→Y 기준 버전과 Z 추가 버전을 비교한다. A·B1은 같은 Z 업무 요구사항과 계수 규칙을 적용한다.

### 8.1 신규 인터페이스 `N_interface`

다음을 유형별 목록으로 기록한다.

- 플랫폼 간 API 작업
- 업무 이벤트 종류
- Daml 계약·인터페이스
- 공통 테스트용 외부 명령·응답 형식의 추가·변경

범용 HTTP 경로 하나에 명령을 추가했다고 인터페이스 추가가 0이라고 처리하지 않는다. 새 업무 명령·스키마도 별도 기록한다.

같은 정의를 호출한 횟수를 인터페이스 수로 세지 않는다.

### 8.2 기존 변경 단위 `N_changed`

Z 추가 때문에 기존 X·Y에서 실제 수정한 모듈·계약을 기록한다.

- 변경 단위·파일 경로·유형
- 변경 전후 역할
- Z 때문에 필요한 변경 이유

동일 단위의 여러 수정은 한 단위로 집계한다. 신규 Z 코드와 기존 X·Y 변경을 구분한다. 주석·서식 변경은 제외한다.

모듈과 계약은 유형별로 보고하고, 전체 파일 수를 그대로 변경 복잡성이라고 부르지 않는다.

### 8.3 업무 메시지 `N_message`

정상 X→Y→Z 한 건의 애플리케이션 수준 요청·응답·업무 알림을 유형별로 집계한다.

- A의 플랫폼 간 권리 확인·상태 전달·조정 메시지
- B의 업무 애플리케이션과 Participant 사이 거래 제출·결과·상태 관련 메시지
- 실제 업무 구현이 사용하는 재확인·폴링 메시지

같은 물리적 메시지를 발신·수신 양쪽에서 기록해도 한 번만 센다. 요청과 응답은 각각 구분한다.

공통 실험 실행기의 명령·readiness·결과 조회·snapshot 호출은 별도 항목으로 집계한다. 업무 연계 메시지와 합쳐 단일 숫자만 제시하지 않는다.

Canton 내부 합의·네트워크 프로토콜 메시지는 애플리케이션 메시지와 분리한다. 이를 수집하지 못하면 미계측으로 명시한다.

연결 수립·헬스체크·로그 전송 등은 업무 메시지에서 제외하고, 관련 부담이 있으면 별도 기록한다.

### 8.4 예외 경로 `N_exception`

Z 추가로 명시적으로 추가·변경한 오류 조건과 처리 경로를 목록으로 기록한다.

예: 권한 거부, 사용 불가, 중복, 타임아웃, 결과 미확정, 복구.

같은 공통 처리기를 여러 곳에서 호출한다고 매번 별도 분기로 세지 않는다. 서로 다른 업무 책임·복구 동작은 구분한다.

분기 목록에는 구현 위치와 대응 테스트를 연결한다.

### 8.5 해석

네 항목을 하나의 점수로 합산하지 않는다. 각 항목의 기능과 책임이 어디에 배치됐는지 설명한다.

B2에는 S2 연결·권한·재할당·관측을 위한 코드와 운영 설정 부담을 별도 기록한다.

개발시간·변경 줄 수는 참고 자료이며 핵심 우열 판정에 사용하지 않는다.

## 9. ⑦ Synchronizer 재할당 비용

적용 대상은 B2다. B2가 미완료이면 NOT_RUN이며 0으로 기록하지 않는다. B2는 필수 후속 구현이므로 이 상태로 B1·B2 담당 전체를 최종 완료 인계하지 않는다.

계약별로 다음을 수집한다.

```text
T_RAs = t_assignment_complete - t_unassignment_start
T_unavailable = t_usable_S2 - t_unusable_S1
```

정밀 구간 계산에도 제2절의 동일 시계 원칙을 적용한다.

계약별로 다음 시점을 구분한다.

- `t_unassignment_start`: 해당 계약의 Unassignment 시작
- `t_assignment_complete`: 해당 계약의 Assignment 완료 확인
- `t_unusable_S1`: 해당 계약의 S1 사용 불가 확인
- `t_usable_S2`: 해당 계약의 S2 사용 가능 확인

관측기 수신 시각으로 계산하는 경우 이를 관측 기준 구간으로 명시한다.

정확한 내부 시각을 이용하려면 같은 시계에서 기록된 구간이거나 별도로 검증된 공통 시각 기준을 사용해야 한다.

관측 지점과 내부 발생 지점을 혼합하지 않는다.

필요 계약이 여러 개면:

- 계약별 구간과 실제 완료 횟수를 기록한다.
- 전체 준비 구간은 최초 Unassignment 시작부터 필요한 계약 전체의 Assignment 완료까지 별도 제시한다.
- 전체 구간을 계약별 시간 합계로 대신하지 않는다.
- `N_RA`는 성공적으로 재할당된 계약 수를 기준으로 기록한다.
- 논리적 X→Y 경계 전환 횟수 1회와 배치·API 호출·실제 재시도 횟수를 별도 기록한다.

Y의 준비 완료는 필요한 계약 전체의 사용 조건을 충족한 이후다. 이 지연은 `T_A_XY`와 `T_E`에 이미 포함된다.

관측 순서 역전이나 이벤트 누락이 있으면 해당 구간을 유효한 정밀 측정값으로 사용하지 않는다.

## 10. 반복·통계·실험 환경

### 10.1 반복과 실행 순서

- T1은 워밍업 3회 후 본 측정 30회를 수행한다.
- 본 측정 30회는 시도 수다. 실패를 빼고 성공 30회가 될 때까지 보충하지 않는다.
- 추가 측정이 필요하면 별도 배치로 구분한다.
- T3는 지연 없는 T1과 별도 집계한다.
- B2의 T1에서 재할당 구간을 함께 수집하여 중복 실험 부담을 줄인다.
- 모델 실행 순서는 한쪽이 항상 먼저 되지 않도록 교대하고 순서를 기록한다.
- 같은 머신에서 측정할 때 다른 모델의 측정·빌드·대규모 작업을 동시에 수행하지 않는다.

### 10.2 통계

각 시간 지표는 유효한 정상 성공 표본에 대해 다음을 보고한다.

- 표본 수
- P50·P95
- 최솟값·최댓값
- 전체 시도 수와 성공·거부·미완료·계측 무효 건수

백분위 계산은 정렬된 n개 표본에서 `ceil(p × n)`번째 값을 사용하는 nearest-rank 방식으로 고정한다. p는 P50에서 0.5, P95에서 0.95다.

표본이 없으면 null로 표시한다. 30회 수준의 P95는 탐색적인 꼬리 지연 관측이며 안정적인 운영 SLA 추정으로 해석하지 않는다.

합계 지표는 실행별로 먼저 계산한 뒤 통계를 낸다. 구간별 P95를 더하여 전체 P95로 제시하지 않는다.

### 10.3 환경 기록

- OS·CPU·코어·메모리
- 언어·라이브러리·DB·SDK·Canton 버전
- 프로세스·노드·Participant·Synchronizer 구성
- CPU·메모리 제한과 적용 여부
- DB 저장 방식·내구성 설정
- 네트워크·로컬 통신·컨테이너 사용 여부
- 정상 부하·경합 호출 수
- 조회·대기·재시도 설정
- 워밍업·서비스 재시작·실행 순서
- 코드·fixture·명세 버전

한 모델만 내구성을 끄거나 확정 기준을 약화해 속도를 높이지 않는다. 같은 머신 사용만으로 자원 조건이 완전히 같다고 주장하지 않는다.

## 11. 유효성·실패·보고

다음 결과는 분리한다.

1. 정상 업무 성공과 유효 계측
2. 기대된 업무 거부
3. 정합성·기능 결함
4. 미완료·결과 미확정
5. 계측·환경 증거 부족

시간 표본을 제외한 경우 실행 ID와 제외 사유를 남긴다. 느리다는 이유만으로 표본을 제외하지 않는다.

관측 한도에 도달한 실행을 0ms나 한도 값으로 대체하지 않는다.

결과표에는 정상 T1, T2, T3, B2/T4를 분리하여 제시한다. 인수 테스트의 PASS/FAIL과 성능·비용 수치를 별도 항목으로 보고한다.

각 실행의 원시 로그와 다음 산출물을 보존한다.

- 공통 실행 설정
- 실행별 결과·계산값
- 집계표와 계산 방법
- 정합성 검증 결과
- 연결 복잡성 목록과 증빙
- 미측정 항목·한계·재현 절차

공통 지표·관측 경계·제외 기준은 결과를 본 뒤 임의로 변경하지 않는다. 변경은 연구 총괄 승인 후 기록하고 영향을 받는 비교를 다시 수행한다.
