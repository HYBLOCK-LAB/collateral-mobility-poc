# 공통 업무 명세 — 기관 간 담보 이동성 비교 PoC

상태: 연구 총괄이 검토·승인한 상세 업무 명세. 인터페이스·인수 기준·계측 명세까지 확정한 후 spec-v1.0으로 고정하며, 현재는 아직 spec-v1.0이 아니다.

## 1. 목적과 적용 범위

독립적인 금융 업무 플랫폼에서 국채 담보가 Repo → 증권대차 → CCP 증거금 배정으로 연속 활용되는 과정을 구현한다.

동일한 금융 업무·권한·성공 및 거부 조건을 다음 모델에 적용한다.

| 모델 | 범위 |
|---|---|
| A | 독립 DB X·Y·Z와 API/이벤트 기반 연계. 필수 |
| B1 | 플랫폼별 Participant와 공통 Synchronizer S1을 사용하는 Canton 구현. 필수 |
| B2 | B1을 활용하여 X→Y 경계의 필요한 계약을 S1→S2로 1회 재할당. 필수 구현. B1 기준 보존 후 개발 병행 가능 |

핵심 비교는 A vs B1이다. B1 코드·환경·증거를 보존한 별도 브랜치·상태·DB·로그에서 B2 구현·개발용 검증을 B1 최종 검증과 병행할 수 있다. B2 최종 기능 인수에는 A·B1 최종 검증과 B2 필수 검증이 필요하며 T1 계측은 요구하지 않는다. B2 비교 실험(T4)은 A·B1 선행 T1 계측과 B2 최종 검증을 확보한 후 수행한다. A·B1·B2 모두 구현 대상이며 B2는 생략 가능한 항목이 아니다.

이 문서는 업무 의미와 정합성 조건을 정한다. API·JSON·오류 코드는 `interface.md`, 구체적인 테스트 입력과 기대 결과는 `acceptance.md`, 이벤트·로그·측정식은 `measurement.md`에서 정한다.

## 2. 실제 금융 관계와 PoC의 모사 범위

### 2.1 유지하는 금융 관계

Repo에서 취득한 증권의 재사용과, 만기에 동등증권을 반환하는 의무는 구분된다. ICMA의 Repo 지침 역시 재사용과 동등증권 반환 관계를 설명한다. [ICMA Repo 지침](https://www.icmagroup.org/assets/ERCC-Guide-to-Best-Practice-March-2025.pdf)

증권대차에서는 차입 국채의 후속 사용과 차입자의 동등증권 반환 의무를 구분한다. ISLA 자료는 증권대차의 소유권 이전 구조와 동등증권 반환 의무를 설명하며, 대차 담보의 반환·해제 방식은 계약 구조에 따라 구분한다. [ISLA GMSLA 안내](https://www.islagroup.org/gmsla-title-transfer/), [ISLA 금융거래 원칙 설명](https://docs.islaemea.org/download/latest/preparing-the-global-master-securities-lending-agreement-gmsla-for-an-evolving-digital-asset-landscape-21-november-2022)

이 자료는 업무 모형을 구성하는 참고 근거다. 본 PoC가 국내 특정 계약의 법적 효력을 재현하거나 판정하는 것은 아니다.

### 2.2 명시적인 실험 가정

- A은행은 실험 시작 시 대상 국채 묶음을 적법하게 보유하고 사용할 수 있다.
- Repo 계약은 B은행의 재사용을 허용한다.
- 증권대차 계약은 C은행의 CCP 담보 제공을 허용한다.
- CCP는 대상 국채를 해당 증거금 요구에 사용할 수 있는 적격 담보로 인정한다.
- Repo·증권대차의 필요한 거래 합의는 사전에 성립해 있다. 협상·호가·승인 화면은 구현하지 않는다.
- 증권대차의 별도 담보 제공은 조건과 제공 완료 여부를 모사한다. 해당 조건이 충족되지 않으면 증권대차를 확정할 수 없다.
- 평가액·헤어컷·적격성 조건은 공통 테스트 데이터에 고정한다. 실시간 평가와 추가 담보 관리는 구현하지 않는다.

이 가정들은 모든 Repo·증권대차·CCP 규정에 보편적으로 적용되는 사실을 뜻하지 않는다.

### 2.3 구현에서 제외하는 사항

실제 현금 결제, 증권 인도, CSD·CCP 운영 시스템 연동, 법적 소유권·담보권 이전, 만기 반환 실행, 이자·수수료·쿠폰 정산, 리콜·청산·디폴트 처리는 구현하지 않는다.

다만 관련 권리·의무가 존재한다는 사실과 후속 거래 후에도 유지되는 관계는 기록한다. 모사된 거래 확정을 실제 결제 완결성으로 해석하지 않는다.

## 3. 참여자·플랫폼·담보 처리 단위

### 3.1 참여자와 플랫폼

| 구분 | 역할 |
|---|---|
| A은행 | Repo의 증권 제공자. 환매 관련 의무와 동등증권 반환 청구 관계를 가진다. |
| B은행 | Repo로 취득한 국채를 재사용하는 증권대차 대여자. A은행에 대한 의무와 C은행에 대한 청구 관계를 가진다. |
| C은행 | 증권대차 차입자이자 CCP 증거금 제공자. B은행에 동등증권을 반환할 의무를 가진다. |
| CCP | 모사된 증거금 요구의 수취 주체. 배정된 묶음의 추가 사용을 제한한다. |
| 플랫폼 X | Repo 업무와 관련 상태를 관리한다. |
| 플랫폼 Y | 증권대차 업무와 관련 상태를 관리한다. |
| 플랫폼 Z | CCP 증거금 배정과 잠금 상태를 관리한다. |

플랫폼은 독립적인 업무·상태 관리 경계다. 기관과 플랫폼은 일대일 관계가 아니며, B은행은 X·Y에, C은행은 Y·Z에 참여한다.

### 3.2 담보 처리 단위

- 국채 100억 원 상당의 **전체 묶음**만 처리한다.
- 묶음은 실험 내 고유 식별자와 종목 식별자, 고정된 수량·기준 평가액을 가진다.
- 100억 원은 기준 평가액이며 국채 액면 수량과 동일한 값으로 취급하지 않는다.
- 부분 배정·분할·병합은 허용하지 않는다.
- 같은 종목의 서로 다른 묶음은 별도 자산으로 구분한다.
- 동일 거래 흐름에서는 X·Y·Z가 같은 묶음 식별자를 사용한다.
- 반복 실험은 실행 식별자로 구분하고, 이전 실행의 계약·요청·잠금이 다음 실행에 영향을 주지 않게 한다.

구체적인 필드명·자료형·수량 단위는 공통 스키마에서 정한다.

## 4. 구분하여 관리할 업무 정보

아래 정보는 공통 업무 의미다. A와 B가 물리적으로 같은 테이블·계약 구조를 사용할 필요는 없다.

| 정보 | 의미 |
|---|---|
| 국채 묶음 | 종목·수량·기준 평가액을 가진 실험 대상 |
| 현재 사용 권리 | 해당 묶음을 다음 거래에 사용할 수 있는 주체와 범위 |
| 재사용·후속 사용 권한 | 증권대차 또는 CCP 배정에 사용할 수 있다는 계약상 허용 |
| Repo 계약 | A·B 간 거래와 환매·반환 관련 관계 |
| 증권대차 계약 | B·C 간 대여·차입, 대차 담보 조건, 동등증권 반환 관계 |
| 반환 의무 | 의무자·권리자·대상 종목·수량·관련 계약·미이행 상태 |
| CCP 배정 | C은행의 묶음을 특정 증거금 요구에 배정한 기록 |
| 잠금 | 배정된 묶음의 추가 사용을 금지하는 상태 |
| 업무 버전·이력 | 이전 상태를 근거로 한 요청의 경합 판정과 변경 추적 |

반환 의무와 현재 사용 권리는 별개다.

예를 들어 Y의 증권대차가 확정되면:

- C은행은 후속 사용 가능한 국채 권리를 가진다.
- B은행은 같은 묶음을 다시 사용할 수 없다.
- C은행의 B은행에 대한 동등증권 반환 의무가 남는다.
- B은행의 A은행에 대한 Repo 관련 의무도 남는다.
- B은행의 반환 청구권을 현재 사용 가능한 국채 권리로 계산하지 않는다.

Repo의 환매대금 지급 관계와 증권대차의 별도 담보 반환·해제 관계는 관련 계약에 기록한다. 금액 산정과 실제 이행은 모사하지 않는다.

## 5. 권한과 사전 합의

### 5.1 업무 수행 권한

| 업무 | 필요한 업무상 권한·합의 |
|---|---|
| Repo 확정 | A·B은행의 거래 합의, A은행의 대상 묶음 사용 권한 |
| 증권대차 확정 | B·C은행의 거래 합의, B은행의 현재 사용 권리와 재사용 허용 |
| CCP 배정 확정 | C은행의 배정 권한, 후속 사용 허용, 모사된 CCP 수락 조건 |
| B2 재할당 | Canton의 관련 계약·Participant·Synchronizer 조건 충족 |

사전 합의는 공통 테스트 데이터로 준비할 수 있으나, 실제 요청자가 해당 업무를 수행할 권한이 있는지 확인하는 절차를 생략하지 않는다.

요청 본문의 `actor` 값만 신뢰하여 다른 기관의 권한을 인정해서는 안 된다. 구현별 인증·위임 방식은 달라도 동일한 업무상 허용·거부 결과를 제공해야 한다.

### 5.2 가시성과 권한의 구분

계약이나 상태를 조회할 수 있다는 사실만으로 해당 묶음을 사용할 수 있는 것은 아니다.

후속 사용에는 현재 권리, 사용 허용 조건, 최신 유효 상태와 제출 권한이 모두 필요하다. 실험 관측기는 정합성 검증에 필요한 정보를 읽을 수 있지만, 그 관측 권한이 업무 거래 권한으로 사용되어서는 안 된다.

## 6. 정상 거래의 상태 전이

아래 상태명은 공통 정규화 결과를 위한 제안이다. 내부 DB 상태나 Daml 계약 이름을 강제하지 않는다.

| 시점 | 현재 사용 권리 | 이전 권리의 처리 | 계약·의무 | CCP 배정 |
|---|---|---|---|---|
| 초기 | A은행이 전체 묶음 사용 가능 | 해당 없음 | Repo·증권대차 미확정 | 없음 |
| X Repo 확정 후 | B은행이 계약 범위 내 재사용 가능 | A은행의 동일 묶음 직접 사용 불가 | Repo 유효, 환매·반환 관련 의무 미이행 | 없음 |
| Y 증권대차 확정 후 | C은행이 CCP 담보 제공 가능 | B은행의 동일 묶음 재사용 권리 소진 | Repo·증권대차 유효, 기존 의무 유지, C→B 반환 의무 추가 | 없음 |
| Z 배정 확정 후 | C은행의 추가 사용 불가 | 후속 거래에 사용할 자유로운 권리 없음 | 기존 계약·의무 유지 | 해당 증거금 요구에 전체 묶음 배정·잠금 |

CCP 배정 후에도 `owner = CCP`라는 값만으로 결과를 표현하지 않는다. 배정 주체 C은행, 수취 주체 CCP, 증거금 요구, 배정 묶음, 잠금 상태를 구분한다.

### 6.1 X — Repo 확정

**전제 조건**

- 대상 묶음이 존재하고 A은행이 사용할 수 있다.
- 상충하는 예약·거래·잠금이 없다.
- A·B은행의 거래 합의와 요청 권한이 유효하다.
- B은행의 재사용 허용 여부가 명시돼 있다.

**확정 효과**

- Repo 계약과 환매·반환 관련 의무가 기록된다.
- A은행의 기존 자유 사용 권리는 소진된다.
- B은행의 국채 사용 권리가 생성된다.
- 후속 사용은 Repo에 기록된 허용 범위로 제한된다.

### 6.2 Y — 증권대차 확정

**전제 조건**

- X의 Repo가 확정돼 있다.
- B은행의 현재 권리가 유효하고 아직 다른 거래에 사용되지 않았다.
- B은행의 재사용이 허용돼 있다.
- B·C은행의 증권대차 합의가 유효하다.
- 별도 대차 담보 제공 조건과 모사된 제공 완료 여부가 충족된다.
- C은행의 후속 담보 사용 허용 여부가 명시돼 있다.

**확정 효과**

- B은행의 동일 묶음 사용 권리가 소진된다.
- C은행의 국채 사용 권리가 생성된다.
- 증권대차 계약과 C→B 동등증권 반환 의무가 기록된다.
- Repo 계약과 기존 의무는 유지된다.
- 별도 대차 담보는 이 국채 묶음과 다른 대상으로 표현한다. 동일 묶음을 자기 자신의 대차 담보로 중복 사용하지 않는다.

### 6.3 Z — CCP 배정 확정

**전제 조건**

- Y의 증권대차가 확정돼 있다.
- C은행의 현재 권리가 유효하고 CCP 제공이 허용돼 있다.
- 모사된 증거금 요구가 존재하며 미충족 상태다.
- 해당 요구는 전체 묶음을 수용하도록 공통 데이터에 설정돼 있다.
- CCP 적격성·수락 조건이 충족된다.
- 대상 묶음에 기존 배정·잠금이나 상충하는 사용이 없다.

**확정 효과**

- 묶음 전체가 해당 증거금 요구에 배정된다.
- 묶음의 추가 사용이 금지된다.
- 모사된 증거금 요구가 충족 상태가 된다.
- Repo·증권대차 계약과 미이행 의무는 유지된다.

배정 해제·교체·반환은 이번 구현 범위에서 제외한다.

## 7. 경합과 상태 일관성

### 7.1 반드시 유지할 조건

1. 동일 묶음에는 동시에 상충하는 사용 가능 권리가 존재할 수 없다.
2. 사용 권리를 조회한 사실만으로 다음 거래의 사용 권리를 확보한 것으로 간주하지 않는다.
3. 새로운 권리를 유효하게 만드는 시점에는 이전 권리를 다시 사용할 수 없어야 한다.
4. CCP에 잠긴 묶음은 새 증권대차나 다른 CCP 배정에 사용할 수 없다.
5. 후속 거래는 기존 계약·반환 의무를 삭제하거나 이행 완료로 바꾸지 않는다.
6. 거부된 요청은 그 요청으로 인한 업무 효과를 남기지 않는다.
7. 중간 처리 상태가 있더라도 동일 묶음이 양쪽에서 사용 가능해져서는 안 된다.
8. 로컬 복제본·캐시가 늦게 갱신될 수는 있지만, 오래된 정보만으로 추가 사용을 확정해서는 안 된다.

A의 분리 DB는 예약·버전 검사·잠금·재확인·복구 등 합리적인 방법을 사용할 수 있다. B는 계약의 유효성과 소비 제약 등 자체 방식을 사용할 수 있다. 두 모델에 같은 내부 처리 단계를 강제하지 않는다.

Daml에서는 계약 소비·보관 처리가 해당 계약의 후속 사용을 제한하는 수단이 될 수 있다. 다만 Daml 계약이 기술적으로 보관됐다는 사실을 Repo나 반환 의무의 경제적 종료와 동일시하지 않는다. [Digital Asset 원장 구조 문서](https://archived.docs.digitalasset.com/overview/3.4/explanations/ledger-model/ledger-structure.html)

### 7.2 최소 경합 시나리오

- **같은 요청 재전송:** 한 업무 효과만 발생한다.
- **서로 다른 증권대차 요청의 경합:** 같은 B은행 권리를 대상으로 두 요청이 경쟁하면 최대 하나만 확정된다.
- **서로 다른 CCP 배정 요청의 경합:** 같은 C은행 권리를 대상으로 두 배정이 경쟁하면 최대 하나만 확정된다.
- 이미 사용된 이전 권리를 근거로 한 새 요청은 확정될 수 없다.

경합의 승자는 미리 지정하지 않는다. 성공 수와 거부 수, 최종 권리·의무·배정 상태를 검증한다.

## 8. 요청 결과·멱등성·복구

### 8.1 요청 결과와 업무 상태의 구분

| 요청 결과 | 의미 |
|---|---|
| 처리 중 | 요청이 진행 중이며 최종 결과가 아직 없다. |
| 확정 성공 | 필요한 업무 효과가 유효하게 확정됐다. |
| 확정 거부 | 업무 조건 또는 권한을 충족하지 못해 해당 요청의 효과가 발생하지 않았다. |
| 결과 미확정 | 타임아웃·응답 유실 등으로 관측자가 최종 결과를 아직 알 수 없다. |

결과 미확정은 계약의 실패·취소·반환을 의미하지 않는다.

X·Y·Z는 별도 거래이므로 Z의 거부가 이미 확정된 X·Y를 자동 취소하지 않는다. Y가 거부되면 기존 B은행 권리가 유지되고, Z가 거부되면 기존 C은행 권리가 유지되는 것이 정상적인 업무 결과다.

### 8.2 멱등성

- 같은 실행·요청 주체·요청 식별자와 동일한 업무 내용의 재전송은 같은 논리적 요청으로 취급한다.
- 이미 성공한 요청의 재전송으로 계약·반환 의무·배정이 추가 생성돼서는 안 된다.
- 같은 요청 식별자에 다른 업무 내용을 보내면 충돌로 거부한다. 기존 요청의 결과는 변경하지 않는다.
- 처리 중이거나 결과 미확정인 요청은 원래 요청의 결과를 추적한다.
- 조건 변경 후 새로운 업무를 요청하려면 새 요청 식별자를 사용한다.
- 기술적 재시도는 원래 요청과 연결해 기록한다.

내부 Canton 오류나 중복 거부를 그대로 최종 업무 결과로 노출할 필요는 없다. 공통 결과는 원래 요청의 실제 확정 여부를 기준으로 정규화한다.

### 8.3 최소 지연·복구 범위

T3의 초기 장애는 **Y 증권대차 처리 결과의 응답 지연으로 요청자가 타임아웃을 경험하는 상황**으로 제한한다.

- 요청자는 타임아웃만으로 실패나 권리 복원을 결정하지 않는다.
- 원래 요청 식별자로 결과를 재확인하거나 안전하게 재시도한다.
- 실제 거래가 이미 확정됐다면 기존 성공 결과를 확인한다.
- 미확정 거래가 진행 중이라면 추가 사용을 막는 보호 상태를 유지한다.
- 복구 완료는 최종 결과를 확인하고 관련 권리·계약·의무가 그 결과와 일치하는 상태다.
- 단순히 응답 지연을 제거한 시점과 업무 복구 완료를 구분한다.

지연 위치·길이·타임아웃·재시도 상한은 `acceptance.md`에서 공통으로 정한다. 계측 시점은 Phase 4의 이벤트 정의를 유지한다.

이 실험은 응답 지연과 그에 따른 결과 확인·재시도를 평가한다. 프로세스 강제 종료, DB 손실, 네트워크 분할 등 모든 장애에 대한 복구 능력을 검증한 것으로 해석하지 않는다.

## 9. 후속 거래 준비 완료와 최종 성공 판정

### 9.1 준비 완료

후속 플랫폼에서 아래 조건을 확인해 정상적인 다음 거래를 제출할 수 있는 시점을 준비 완료로 본다.

- 필요한 선행 거래가 확정돼 있다.
- 현재 권리와 사용 허용 조건을 확인할 수 있다.
- 필요한 계약·상태가 유효하다.
- 요청 주체의 업무 권한과 사전 합의가 충족된다.
- B2라면 필요한 계약을 대상 Synchronizer에서 사용할 수 있다.

준비 완료는 미래의 경합까지 배제하는 성공 보장이 아니다. 실제 제출·확정 단계에서도 최신 상태와 권한을 검증한다.

### 9.2 정상 X→Y→Z 최종 성공

다음 조건을 모두 충족해야 한다.

- X Repo, Y 증권대차, Z CCP 배정이 순서대로 각각 확정됐다.
- 같은 묶음 전체가 하나의 증거금 요구에 배정·잠금됐다.
- A·B·C은행에게 그 묶음의 상충하는 추가 사용 가능 권리가 없다.
- Repo·증권대차 계약과 미이행 반환 의무가 유지된다.
- 중복 계약·중복 의무·이중 배정이 없다.
- 임시 예약·처리 상태가 남아 정상 완료를 방해하지 않는다.
- 요청·계약·묶음·이벤트를 같은 거래 흐름으로 추적할 수 있다.

실패하거나 미완료된 실행을 정상 성공의 지연시간 표본에 섞지 않는다. 실패·미완료 건수와 도달한 상태는 별도로 보고한다.

## 10. 구현 순서와 평가 보존

- A·B1의 X→Y를 먼저 구현하고 공통 테스트와 계측을 확인한다.
- 플랫폼 연결 복잡성 측정을 위해 X→Y 기준 버전을 보존한 뒤 Z를 추가한다.
- A·B1의 정상 거래, 최소 중복·경합, 응답 지연·복구를 검증한다.
- 이후 B1의 업무 계약·검증·계측을 활용해 B2를 확장한다.
- B2는 필요한 계약을 X→Y 경계에서 S1→S2로 한 번 재할당한다. 계약 의존성 때문에 함께 필요한 계약은 구현 검토에서 식별하고 기록한다.
- 재할당은 업무상 권리자·반환 의무·계약 경제조건을 바꾸지 않는다.
- 재할당 중에는 대상 계약의 사용 불가 상태를 정상적으로 표현하고, 완료 후 동일 업무를 이어간다.
- 7개 지표와 `End-to-End = Availability + Waiting + Completion` 관계를 유지한다.
- B2가 미완료이면 재할당 비용을 미측정으로 명시하고 B1·B2 담당 전체의 최종 개발 완료로 인계하지 않는다. 최종 인계는 acceptance.md의 필수 공통 테스트 통과·증빙 조건을 충족해야 한다.
- 모든 커밋·푸시는 사용자 확인 후 수행한다.

## 11. 명세 변경 관리

개발 담당자와 Agent는 이 문서의 권리·의무·상태 전이·성공 및 거부 조건을 임의로 변경하지 않는다.

구현 제약이나 충돌을 발견하면 다음을 연구 총괄에게 보고한다.

- 충돌하는 명세와 구현상 제약
- A·B의 업무 동등성과 평가에 미치는 영향
- 기존 규칙을 유지하는 해결 방법
- 변경이 필요할 경우 최소 변경안

공통 규칙 변경은 승인 후 모든 구현·스키마·테스트·계측 문서에 함께 반영한다.
