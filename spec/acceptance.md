# 공통 인수 기준 — 기관 간 담보 이동성 비교 PoC

상태: 연구 총괄이 검토·승인한 인수 기준. 세부 fixture·Schema·계측 설정은 후속 작성 및 승인 대상이며, 현재는 아직 spec-v1.0이 아니다.

## 1. 목적과 적용 모델

`business.md`와 `interface.md`의 업무·권한·정합성 규칙을 동일한 입력과 기대 결과로 검증한다.

- A·B1은 공통 필수 테스트를 모두 수행한다.
- B2도 필수 구현 대상이다. B1 기준 보존 후 별도 환경에서 개발용 검증을 병행할 수 있다. B2 최종 기능 인수에는 A·B1 최종 검증과 B2 필수 검증이 필요하며 선행 T1 계측은 요구하지 않는다. T4의 선행 계측 조건은 measurement.md를 따른다. B2에서는 공통 정상 경로·준비 상태·재할당 테스트를 필수 수행한다.
- B2의 경합·복구 테스트 수행 여부는 명시한다. 미수행을 통과로 처리하지 않는다.
- 기능적 동등성과 정합성 검증을 먼저 수행한 뒤 성능 결과를 비교한다.
- 내부 DB 구조, Daml 계약 개수, 내부 오류 문구가 같아야 할 필요는 없다.

T1~T4는 실험군 구분이다. 아래의 세부 테스트는 해당 실험에 필요한 공통 업무 규칙을 검증한다.

## 2. 공통 실행·판정 규칙

### 2.1 실행 격리

각 독립 테스트와 반복 실행은 새로운 `run_id`를 사용한다.

A·B1·B2에는 같은 내용의 fixture와 요청을 적용한다. 모델 구분을 위해 실행 식별자가 달라지는 경우 비교 시 동일한 테스트 실행으로 연결한다.

다른 테스트의 계약·잠금·멱등성 기록을 재사용하지 않는다.

### 2.2 전제 상태 준비

Repo 확정 상태가 필요한 테스트는 실제 `CONFIRM_REPO` 명령으로 준비한다. 증권대차 확정 상태가 필요하면 실제 X→Y 거래를 수행한다.

DB 직접 수정이나 Daml 계약 직접 주입으로 업무 검증을 건너뛴 상태를 만들지 않는다. 최초 자산·합의·권한 fixture 적재는 허용한다.

테스트 대상 단계 이전의 준비 거래와 테스트 본문을 로그에서 구분한다.

### 2.3 결과 판정

| 판정 | 의미 |
|---|---|
| `PASS` | 기대 결과와 정합성·증빙 조건을 모두 충족 |
| `FAIL` | 정상 실행된 테스트에서 기대한 업무 결과나 정합성 조건을 위반 |
| `INCONCLUSIVE` | 환경 오류·관측 실패 등으로 판단할 증거가 부족 |
| `NOT_RUN` | 실행하지 않음 |
| `NOT_APPLICABLE` | 해당 모델에 적용되지 않음 |

`PENDING`, `UNKNOWN`은 요청의 중간 관측 결과이며 테스트 통과를 의미하지 않는다.

관측 한도까지 결과가 확정되지 않으면 미완료로 보고한다. 테스트 실행 환경의 관측 실패인지, 구현의 복구·진행 실패인지 구분하고 근거를 남긴다.

### 2.4 공통 시간 설정

응답 대기 한도, 조회·재시도 간격, 복구 시도 상한, 최종 관측 한도는 `measurement.md`에서 공통 값으로 확정한다.

- 같은 테스트에는 모든 모델에 같은 값을 적용한다.
- 특정 모델이 통과할 때까지 해당 모델의 설정만 완화하지 않는다.
- 변경이 필요하면 승인 후 비교 대상 전체에 적용하고 다시 실행한다.
- 관측 한도를 실제 금융시장의 결제 기한이나 복구 SLA로 해석하지 않는다.

## 3. 기준 fixture와 예상 업무 상태

### 3.1 정상 fixture F0

| 항목 | 값·조건 |
|---|---|
| 국채 묶음 | `bundle-001`, 전체 묶음만 처리 |
| 종목 | 테스트용 종목 식별자. 실재 국채라는 의미는 없음 |
| 기준 평가액 | `"10000000000"`, `"KRW"` |
| 수량 | 공통 fixture의 고정 수량·단위. 기준 평가액과 별도 관리 |
| 초기 상태 | 버전 0, A은행 사용 가능 |

| 증권대차 합의 | B·C은행, C은행 CCP 제공 허용 |
| 별도 대차 담보 | 대상 국채와 다른 담보 참조, 조건 충족·제공 완료 |
| 증거금 요구 M1 | C은행→CCP, 전체 묶음 수용, 미충족 |

| 권한 | 명령 제출자와 실험 관측기 권한 정상 설정 |

### 3.2 공통 예상 상태

| 상태 | 버전 | 사용 권리 | 거래·의무 | 배정 |
|---|---:|---|---|---|
| S0 초기 | 0 | A 사용 가능 | 확정 거래·관련 의무 없음 | 없음 |
| S1 Repo 확정 | 1 | A 권리 소진, B 사용 가능 | Repo 유효, A→B 환매대금·B→A 동등증권 반환 의무 미이행 | 없음 |
| S2 증권대차 확정 | 2 | A·B 권리 소진, C CCP 제공 가능 | Repo·증권대차 유효, 기존 의무 유지, C→B 동등증권 및 B→C 별도 담보 반환·해제 의무 미이행 | 없음 |
| S3 CCP 배정 | 3 | A·B 권리 소진, C 권리 잠금 | S2의 계약·의무 유지 | 전체 묶음이 M1에 배정·잠금, M1 충족 |

복제본은 같은 공통 식별자로 연결하여 중복 계산하지 않는다.

확인해야 하는 것은 논리적 계약·의무의 존재와 내용이다. 내부 계약 교체 이력이나 보조 기록의 개수를 동일하게 강제하지 않는다.

## 4. T1 — 정상 연속 거래

### AC-01. X→Y→Z 정상 완료

**입력:** F0.

**절차**

1. A은행이 X에 버전 0으로 Repo 확정을 요청한다.
2. X의 확정 성공과 S1을 확인한다.
3. Y의 readiness가 참이 되면 B은행이 버전 1로 증권대차를 제출한다.
4. Y의 확정 성공과 S2를 확인한다.
5. Z의 readiness가 참이 되면 C은행이 버전 2로 CCP 배정을 제출한다.
6. Z의 확정 성공과 S3를 확인한다.

준비 완료 뒤 사람이 승인하거나 임의로 대기하지 않고 자동 제출한다. 실제 제출 대기시간은 기록한다.

**기대 결과**

- 신규 업무 요청 3개가 각각 한 번 확정된다.
- 버전은 0→1→2→3으로 진행한다.
- 단계별 상태가 S1·S2·S3와 일치한다.
- Repo·증권대차와 관련 의무가 최종 상태에도 유지된다.
- 같은 묶음의 추가 사용 가능 권리가 남지 않는다.
- 중복 배정과 미완료 예약·처리 상태가 없다.
- 제출·확정·로컬 반영·준비 완료 이벤트를 구분하여 추적할 수 있다.

기능 확인 후 T1 반복 측정을 진행한다. 모델별 최소 30회를 초기 목표로 하며, 상세 반복·워밍업 규칙은 `measurement.md`를 따른다.

### AC-02. Readiness의 비변경성

S0에서 Y, S1에서 Y, S2에서 Z의 readiness를 조회한다.

**기대 결과**

- 필요한 선행 거래가 없으면 준비 완료로 보고하지 않는다.
- 정상 조건을 충족하면 해당 후속 업무에 대해 준비 완료를 보고한다.
- 반복 조회만으로 버전·권리·계약·의무·배정이 바뀌지 않는다.
- readiness 조회는 권리를 예약하지 않는다.

## 5. 권한·업무 조건 거부

각 변형은 독립 실행에서 하나의 주된 거부 원인을 갖도록 준비한다. 공통 준비 조건까지 유효한 것을 확인한 뒤 테스트 명령을 보낸다.

### AC-03. 인증·권한·입력 검증

| 변형 | 입력 | 기대 결과 |
|---|---|---|
| 인증 실패 | 자격 정보 누락·유효하지 않은 자격 정보 | `UNAUTHENTICATED`, 업무 효과 없음 |
| 명령 권한 부족 | 정상 인증된 C은행이 X의 Repo 확정 요청 | `FORBIDDEN`, 업무 효과 없음 |
| 타 기관 결과 접근 | 관계없는 기관이 다른 주체의 요청 결과 조회 | 접근 거부, 결과 내용 미노출 |
| 관측 권한 부족 | 일반 업무 자격으로 전체 snapshot 조회 | 접근 거부, snapshot 미노출 |
| 형식 오류 | 필수 값 누락·잘못된 자료형·추가 필드 | `INVALID_REQUEST`, 업무 효과 없음 |
| 잘못된 플랫폼 | Y에 Repo 확정 명령 제출 | `INVALID_REQUEST`, 업무 효과 없음 |

`FORBIDDEN`은 인증된 주체의 권한 부족을 나타낸다. 연구 총괄 승인에 따라 `interface.md`에도 반영한다.

### AC-04. 금융 업무 전제 검증

| 변형 | 준비·요청 | 기대 결과·유지 상태 |
|---|---|---|
| 재사용 불허 | Repo 재사용 허용을 false로 둔 fixture로 X 확정 후 Y 요청 | `USE_NOT_PERMITTED`, S1 유지 |
| 대차 담보 미제공 | 제공 완료만 false로 둔 fixture로 X 확정 후 Y 요청 | `PRECONDITION_NOT_MET`, S1 유지 |
| 대차 담보 조건 미충족 | 제공은 완료지만 조건 충족만 false로 두고 Y 요청 | `PRECONDITION_NOT_MET`, S1 유지 |
| C 후속 사용 불허 | C의 CCP 제공 허용을 false로 두고 Y까지 확정 후 Z 요청 | `USE_NOT_PERMITTED`, S2 유지 |
| CCP 적격성 미충족 | 적격성만 false로 두고 Y까지 확정 후 Z 요청 | `COLLATERAL_NOT_ELIGIBLE`, S2 유지 |

모든 변형에서 기존 계약·의무는 유지하고, 거부된 요청으로 인한 신규 계약·의무·배정을 생성하지 않는다.

C의 후속 사용이 불허돼도 증권대차 자체의 다른 조건이 유효하면 Y는 확정될 수 있다. 거부 대상은 허용되지 않은 Z의 후속 사용이다.

### AC-05. 선행 거래·버전·잠금 검증

| 변형 | 절차 | 기대 결과 |
|---|---|---|
| 선행 거래 없음 | S0에서 Y 또는 Z에 해당 초기 버전으로 제출 | `PRECONDITION_NOT_MET` 또는 `RIGHT_UNAVAILABLE`, S0 유지 |
| 오래된 버전 | S1에서 새 요청 ID로 버전 0의 Y 명령 제출 | `VERSION_CONFLICT`, S1 유지 |
| 잠금 후 추가 배정 | S3에서 새 미충족 요구 M2와 새 요청 ID로 같은 묶음 배정 | `RIGHT_UNAVAILABLE` 또는 `PRECONDITION_NOT_MET`, S3 유지, M2 미충족 |

잠금 검증에서는 버전 3과 유효한 M2를 사용한다. 버전 오류나 M1의 기충족만으로 거부되어 잠금 검증을 대신하지 않게 한다.

## 6. T2 — 중복·경합

### AC-06. 확정 성공 후 동일 요청 재전송

Repo·증권대차·CCP 배정 단계별로 검증한다.

**절차**

1. 대상 명령을 정상 확정한다.
2. 같은 플랫폼에 동일 요청 ID와 같은 업무 내용을 두 번 재전송한다.

**기대 결과**

- 최초 업무 효과는 한 번만 발생한다.
- 재전송은 원래 확정 성공과 같은 거래·전후 버전을 반환한다.
- 재전송 결과의 `replayed`는 true다.
- 현재 버전이 이미 증가했어도 원래 요청을 버전 충돌로 바꾸지 않는다.
- 재전송으로 업무 버전·계약·의무·배정이 추가되지 않는다.

호출 수와 논리적 업무 성공 수를 구분한다. 같은 성공 결과를 세 번 받았다고 세 건의 거래 성공으로 세지 않는다.

### AC-07. 같은 요청 ID에 다른 내용

**절차**

1. Y의 증권대차 요청을 정상 확정한다.
2. 같은 인증 주체·요청 ID를 유지하고 `loan_id`를 다른 값으로 바꿔 재전송한다.

**기대 결과**

- 변경한 요청은 `REQUEST_ID_CONFLICT`로 거부한다.
- 원래 요청 결과는 성공 상태로 유지한다.
- 변경된 `loan_id`의 거래·의무를 생성하지 않는다.
- 버전과 권리는 원래 확정 결과를 유지한다.

### AC-08. 동일 요청 동시 제출

**준비:** S1.

같은 B은행 자격·요청 ID·업무 내용의 Y 요청 두 개를 공통 시작 장벽에서 동시에 제출한다.

**기대 결과**

- 논리적 증권대차는 정확히 한 번 확정된다.
- 접수 시점에 PENDING·UNKNOWN을 관측할 수 있지만, 결과 확인 후 두 호출은 같은 원래 업무 결과로 연결된다.
- 동일 요청의 중복 제출이라는 이유만으로 원래 업무 결과를 최종 거부로 바꾸지 않는다.
- S2에 도달하며 버전은 한 번만 증가한다.
- 계약·의무가 중복 생성되지 않는다.

### AC-09. 서로 다른 증권대차 요청 경합

**준비:** S1.

유효한 같은 합의를 참조하되 서로 다른 `request_id`·`loan_id`를 가진 두 Y 요청을 버전 1로 동시에 제출한다.

**기대 결과**

- 정확히 한 요청이 확정 성공한다.
- 다른 요청은 최종적으로 `VERSION_CONFLICT` 또는 `RIGHT_UNAVAILABLE`로 거부된다.
- 두 요청 모두 성공하거나, 정상 환경에서 둘 다 최종 거부되는 결과는 통과가 아니다.
- S2에 도달하며 증권대차와 관련 의무는 한 거래분만 생성된다.
- 이전 B은행 권리가 다시 사용 가능해지지 않는다.

### AC-10. 서로 다른 CCP 배정 요청 경합

**준비:** S2와 같은 묶음을 수용할 수 있는 미충족 요구 M1·M2.

서로 다른 `request_id`·`allocation_id`를 가진 Z 요청 두 개가 각각 M1·M2를 대상으로 버전 2에서 경쟁한다.

**기대 결과**

- 정확히 하나의 배정만 확정된다.
- 다른 요청은 `VERSION_CONFLICT` 또는 `RIGHT_UNAVAILABLE`로 거부된다.
- 승리한 요구 하나만 충족되고 다른 요구는 미충족이다.
- 묶음은 한 배정에만 잠기고 버전은 3이다.
- 기존 Repo·증권대차와 의무는 유지된다.

### 경합 실행 조건

- 동일 요청 동시 제출과 서로 다른 요청 경합을 구분한다.
- 클라이언트의 공통 시작 장벽으로 제출을 시작한다.
- 서버 접수·처리 로그로 실제 겹침 여부를 확인한다.
- 단순히 첫 요청이 끝난 뒤 두 번째가 실행된 사례만으로 동시 처리 안전성을 검증했다고 주장하지 않는다.
- AC-08~10은 각각 독립 실행 10회를 초기 기준으로 한다.
- 실제 중첩이 관측되지 않으면 증거 부족으로 명시하고 실행 조건을 점검한다.
- 높은 요청량의 스트레스 테스트로 확대하지 않는다.

## 7. T3 — Y 응답 지연·복구

### AC-11. 확정 결과 응답 지연 후 재확인·재전송

**준비:** S1.

**주입 대상**

Y의 증권대차 처리 결과를 원래 제출자에게 돌려주는 첫 응답을 지연시킨다.

지연 장치는 업무 권리·DB·계약을 직접 변경하지 않는다. 원래 명령은 계속 처리되며 요청자는 응답 대기 한도를 넘겨 UNKNOWN을 관측한다.

실제 지연 경계·타이밍은 공통 설정으로 고정한다. 정상 처리 자체가 늦어 발생한 타임아웃과 주입된 응답 지연을 구분할 수 있도록 내부 확정·응답 보류 로그를 남긴다.

**절차**

1. Y 증권대차를 제출하고 첫 결과 응답을 보류한다.
2. 요청자의 타임아웃과 UNKNOWN 관측을 기록한다.
3. 원래 요청 ID로 결과를 조회한다.
4. 결과가 미확정이면 공통 복구 정책에 따라 조회·안전한 재전송을 수행한다.
5. 확정 성공을 확인한 뒤 같은 요청을 한 번 재전송해 원래 결과 반환을 검증한다.
6. 지연된 응답과 이미 확인한 결과가 서로 다른 신규 거래로 집계되지 않는지 확인한다.
7. Z의 준비 완료를 확인하고 정상 배정을 수행한다.

응답 지연은 원래 제출 호출에 적용한다. 복구용 조회·후속 재전송까지 계속 차단하는 장애로 확대하지 않는다.

**기대 결과**

- 원래 Y 요청은 정확히 한 번 확정된다.
- UNKNOWN을 확정 거부로 덮어쓰거나 B은행 권리를 임의 복원하지 않는다.
- 조회·재전송 결과는 같은 `loan_id`와 원래 확정 결과로 연결된다.
- Y의 복구 완료 시 S2, Z까지 진행한 뒤 S3와 일치한다.
- 중복 계약·의무·배정과 미완료 예약이 없다.
- 주입·타임아웃·재확인·재시도·복구 완료를 추적할 수 있다.

복구 시간, 재시도, 미완료 건수와 지연 영향은 `measurement.md`에 따라 계산한다. 조회 횟수와 명령 재제출 횟수는 구분해 기록한다.

이 테스트 통과를 프로세스 중단·DB 손실·네트워크 분할에 대한 복구 검증으로 확대하지 않는다.

## 8. T4 — B2 재할당

### AC-12. S1→S2 재할당 후 정상 후속 거래

**적용:** B2만. A·B1은 NOT_APPLICABLE.

**준비:** X의 Repo가 S1에서 확정된 S1 업무 상태.

**절차**

1. 재할당 전 업무 권리·계약·의무·버전을 기록한다.
2. `REASSIGN_FOR_LENDING`으로 필요한 계약을 S1→S2로 재할당한다.
3. 실제 Unassignment·Assignment와 사용 불가·사용 가능 이벤트를 수집한다.
4. 재할당 완료 후 Y의 준비 완료를 확인한다.
5. Y 증권대차와 Z CCP 배정을 순서대로 확정한다.

**기대 결과**

- 재할당 자체는 B은행의 권리자·업무 버전 1·Repo 조건·관련 의무를 바꾸지 않는다.
- 재할당된 계약은 S1·S2에서 동시에 사용할 수 없다.
- 필요한 계약이 S2에서 사용 가능해진 뒤 Y 거래를 진행한다.
- 최종 업무 상태는 S3와 같다.
- Y→Z에서 추가 재할당이 발생하지 않는다.
- 하나의 X→Y 경계 전환에 포함된 실제 계약 목록과 계약별 재할당 기록을 남긴다.

업무 계약이 여러 개라는 이유로 실제 계약별 재할당 횟수를 임의로 1로 축약하지 않는다. 논리적 경계 전환과 실제 재할당 횟수의 계수 방식은 `measurement.md`에서 구분한다.

재할당 중 장애 주입·수동 복구는 이번 인수 범위에 포함하지 않는다.

## 9. 상태 일관성 검증 증거

최종 snapshot과 거래·권리 이력을 함께 검증한다.

필수 확인 사항:

- 같은 묶음의 유효한 사용 가능 권리가 중복 생성되지 않음
- 경합에서 동일 선행 권리를 근거로 둘 이상의 상충 거래가 확정되지 않음
- 한 번 소진·잠금된 권리가 응답 지연이나 재시도 때문에 복원되지 않음
- 후속 거래 후에도 선행 계약과 미이행 의무가 유지됨
- 다른 플랫폼의 같은 논리 기록을 중복 권리로 세지 않음
- 오래된 로컬 복제본을 현재 권위 있는 사용 권리로 해석하지 않음

서로 다른 시점에 수집한 snapshot에 과거·현재 권리가 함께 보인다는 이유만으로 이중 사용으로 판정하지 않는다. 실제 유효성·소진 관계와 확정 이력으로 판단한다.

반대로 최종 상태만 정상이라는 이유로 중간 이중 사용이 없었다고 단정하지 않는다. 증빙이 부족하면 검증 범위와 한계를 기록한다.

공통 이벤트·이력 필드와 검증기 입력은 Schema·`measurement.md`에서 확정한다.

## 10. 플랫폼 연결 복잡성 검증 준비

A·B1·B2에 다음 절차를 적용한다.

1. X→Y가 동작하고 관련 공통 테스트를 통과한 기준 버전을 보존한다.
2. 동일한 Z 업무 요구사항을 추가한다.
3. 신규 인터페이스, 기존 X·Y 변경, 업무 메시지, 예외·복구 분기를 기록한다.
4. Z 추가 후 공통 테스트를 다시 수행한다.

검증 근거는 기준·추가 버전, 변경 목록과 사유, 인터페이스 정의, 실행 로그다.

API와 Daml 계약·인터페이스의 개수를 단순 합산해 우열을 판단하지 않는다. 내부 구현 방식의 차이를 기록하고 같은 기능의 추가에 필요한 변경을 비교한다.

기준 버전 보존을 위한 커밋도 사용자 확인 후 수행한다.

## 11. 완료 기준과 보고

A·B1의 필수 인수 기준:

- AC-01~11 통과
- 단계별 권리·계약·의무·배정 상태 검증
- 경합·복구와 최종 정합성의 증빙 확보
- X→Y 기준 버전과 Z 추가 변경 근거 확보
- 측정에 필요한 공통 식별자와 이벤트 연결
- FAIL·INCONCLUSIVE·NOT_RUN 항목을 숨기지 않고 보고

B2의 필수 인수 기준:

- AC-01·02 및 AC-12 수행
- 나머지 공통 테스트의 수행 여부·결과 명시
- 재할당 시간·사용 불가 구간·실제 계약별 횟수 확보

### 최종 개발 완료 제출·인계 조건

| 담당 | 필수 공통 테스트 |
|---|---|
| A 담당 | A의 AC-01~11 |
| B1·B2 담당 | B1의 AC-01~11, 이후 B2의 AC-01·02·12 |

- 각 필수 테스트의 변형·반복·증빙을 공통 실행기로 검증하고 모두 PASS해야 최종 개발 완료로 제출·인계할 수 있다.
- 필수 항목의 FAIL·INCONCLUSIVE·NOT_RUN·증거 누락은 인계 불가다. 수정·환경 복구 후 같은 조건으로 다시 검증한다.
- 공통 실행기가 아직 없거나 자체 테스트만 수행한 상태는 최종 공통 검증 완료가 아니다.
- 의도된 업무 거부는 기대한 오류·상태 보존을 만족하면 테스트 PASS다. 모든 업무 명령의 COMMITTED를 요구하는 것은 아니다.
- 일부 필터 테스트의 통과나 필수 목록·반복·기대 결과를 줄인 결과로 전체 완료를 대신하지 않는다.
- 인계할 코드·명세·fixture와 테스트 증거의 기준이 같아야 한다. 영향을 주는 변경 이후에는 재검증한다.
- 재현 문서·원시 로그·X→Y 기준 버전·Z 추가 변경 근거도 인수 기준대로 제공한다.
- A·B1의 AC-12는 NOT_APPLICABLE이다. B2의 나머지 공통 테스트는 기존 범위대로 수행 여부를 명시하고 미수행을 통과로 처리하지 않는다.
- 미완료 작업의 개발 중 공유는 가능하나 최종 완료 제출과 명확히 구분한다.

공통 실행기 구현 시 연구 총괄이 관리하는 필수 목록·반복·증빙을 검사하는 최종 완료 확인 기능을 둔다. 모든 필수 조건 충족 시에만 종료 코드 0, 하나라도 미충족하면 0이 아닌 코드로 종료한다. 이는 후속 실행기의 구현 요건이며, 현재 GitHub 제출 자동 차단이 구현됐다는 뜻은 아니다.

결과 보고에는 다음을 포함한다.

- 모델·버전·실행 환경
- 테스트 ID·실행 ID·fixture 버전
- 기대 결과와 실제 결과
- PASS/FAIL 등 최종 판정
- 논리적 성공·거부·미완료 요청 수
- 관련 거래·권리·의무·배정 증거
- 로그 위치와 실패 원인 또는 관측 한계

기능적 오류가 남아 있는 실행의 시간 결과를 정상 성능 표본으로 사용하지 않는다. 구현 결함·실험 환경 실패·측정 한계를 구분한다.
