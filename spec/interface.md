# 공통 인터페이스 명세 — 기관 간 담보 이동성 비교 PoC

상태: 연구 총괄이 검토·승인한 인터페이스 명세. 세부 JSON Schema·fixture·인수 기준·계측 명세는 후속 작성 및 승인 대상이며, 현재는 아직 spec-v1.0이 아니다.

## 1. 적용 범위

승인된 `business.md`를 기준으로 A·B1·B2에 공통 명령·응답·조회·오류 규칙을 적용한다. B2는 필수 범위다. B1 기준 보존 후 별도 환경에서 개발을 병행할 수 있으며, 최종 기능 인수와 비교 실험의 선행 조건은 business.md를 따른다. HTTP/JSON은 공통 테스트를 연결하는 외부 형식이며, 내부 DB·원장·플랫폼 간 연계 방식을 동일하게 만들도록 요구하지 않는다.

실험 실행기의 역할은 제출·대기·조회·계측이다. 별도 중앙 DB에서 업무 권리를 관리하거나 거래 성공 여부를 대신 결정하지 않는다.

## 2. 공통 식별자와 데이터 표현

### 2.1 식별자

| 필드 | 의미 |
|---|---|
| `run_id` | 독립적인 실험 실행 |
| `request_id` | 논리적 업무 요청. 재전송 시 유지 |
| `bundle_id` | 국채 전체 묶음 |
| `security_id` | 국채 종목. 테스트용 식별자 사용 가능 |
| `agreement_id` | 사전에 합의한 Repo 또는 증권대차 조건 |
| `repo_id` | 확정할 Repo 거래 |
| `loan_id` | 확정할 증권대차 거래 |
| `margin_call_id` | 모사된 CCP 증거금 요구 |
| `allocation_id` | CCP 배정 |
| `obligation_id` | 계약상 의무 |

모든 업무 식별자는 공통 테스트 데이터와 요청에서 정한다. 내부 DB 기본키·Canton Contract ID를 공통 업무 식별자로 사용하지 않는다.

내부 식별자는 별도 진단 로그에 기록하여 공통 업무 식별자와 연결할 수 있어야 한다.

### 2.2 자료형

- 식별자와 기관 코드는 문자열이다.
- 기관 코드는 `BANK_A`, `BANK_B`, `BANK_C`, `CCP`를 사용한다.
- 금액·액면 수량은 부동소수점 오차를 피하도록 십진수 문자열로 표현하고 단위를 함께 명시한다.
- 기준 평가액 100억 원은 `"10000000000"`과 통화 `"KRW"`로 표현한다.
- 수량과 기준 평가액은 별도 필드로 관리한다.
- 사용 허용 여부·담보 제공 완료 여부는 boolean이다.
- 업무 버전은 0 이상의 정수다.
- 없는 선택 값은 `null`, 목록이 없으면 빈 배열로 표현한다.
- 구체적인 허용 길이·필수 필드·숫자 형식은 JSON Schema에서 확정한다.

## 3. 사전 준비 데이터

실험 시작 전에 다음 데이터를 같은 내용으로 각 모델에 준비한다.

| 데이터 | 필수 업무 내용 |
|---|---|
| 국채 묶음 | 묶음·종목 식별자, 전체 수량과 단위, 기준 평가액, 초기 A은행 사용 권리 |
| Repo 합의 | A·B은행, 대상 묶음, B은행 재사용 허용 여부, 환매·반환 조건 참조 |
| 증권대차 합의 | B·C은행, 대상 묶음, C은행 후속 사용 허용 여부 |
| 대차 담보 조건 | 별도 담보의 조건 참조·식별자, 조건 충족 여부, 제공 완료 여부 |
| 증거금 요구 | C은행, CCP, 대상 묶음의 수용 조건, 미충족 상태 |
| 권한 설정 | 요청 자격과 기관별 업무 권한 |

공통 fixture 파일을 읽어 준비하되, 모델별 적재 방식은 달라도 된다. 준비 작업은 거래 성능 측정 구간에 포함하지 않고 별도 기록한다.

초기화는 새 `run_id`를 생성하는 방식으로 진행한다. 진행 중인 실행의 데이터를 덮어쓰는 공통 삭제·초기화 API는 이번 범위에 추가하지 않는다.

거래 명령은 사전 합의를 참조한다. 요청자가 `reuse_allowed=true` 같은 값을 보내 기존 합의를 바꾸는 방식은 허용하지 않는다.

거부 테스트는 조건이 다른 fixture를 별도 실행에 준비하여 수행한다.

## 4. 공통 호출 목록

각 플랫폼의 기본 주소는 실행 설정에서 제공한다. 특정 언어·포트 번호는 이 문서에서 강제하지 않는다.

| 호출 | 제공 위치 | 목적 |
|---|---|---|
| `POST /runs/{run_id}/commands` | X·Y·Z | 해당 플랫폼의 명령 제출·재전송 |
| `GET /runs/{run_id}/commands/{request_id}` | 원래 제출한 플랫폼 | 요청 결과 재확인 |
| `GET /runs/{run_id}/readiness` | Y·Z | 다음 거래 제출 준비 상태 확인 |
| `GET /runs/{run_id}/snapshot` | X·Y·Z | 권한 있는 실험 관측기의 로컬 업무 상태 수집 |

X는 Repo, Y는 증권대차, Z는 CCP 배정 명령을 처리한다. B2의 재할당 명령은 X에서 제공한다.

실험 실행기는 X·Y·Z의 snapshot을 수집하여 정합성을 검증한다. snapshot을 합친 결과를 업무상 권위 있는 중앙 장부로 사용하지 않는다.

## 5. 공통 명령

### 5.1 요청 공통 형식

```json
{
  "request_id": "request-loan-001",
  "command_type": "CONFIRM_LOAN",
  "bundle_id": "bundle-001",
  "expected_version": 1,
  "payload": {
    "agreement_id": "loan-agreement-001",
    "loan_id": "loan-001"
  }
}
```

- `run_id`는 URL에서 지정한다.
- `request_id`는 실행 내에서 새 업무 요청마다 구분한다.
- 재전송은 원래 플랫폼·동일 식별자·동일 업무 내용으로 수행한다.
- 요청 주체는 인증 정보에서 식별한다.
- 요청 본문에 기관 이름을 기재하는 것만으로 업무 권한을 부여하지 않는다.
- `expected_version`은 요청이 근거로 삼은 묶음의 업무 버전이다.
- 정해지지 않은 필드·명령 종류·잘못된 자료형은 거부한다.

JSON 필드 순서는 업무 내용의 차이로 보지 않는다.

### 5.2 명령별 내용

| 명령 | 플랫폼·기본 요청 주체 | `payload` |
|---|---|---|
| `CONFIRM_REPO` | X·A은행 | `agreement_id`, `repo_id` |
| `CONFIRM_LOAN` | Y·B은행 | `agreement_id`, `loan_id` |
| `ALLOCATE_MARGIN` | Z·C은행 | `margin_call_id`, `allocation_id` |
| `REASSIGN_FOR_LENDING` | X·B은행, B2만 | `source_synchronizer`, `target_synchronizer` |

기본 요청 주체 외의 참여 기관 합의는 사전 데이터와 구현별 권한 설정으로 확인한다. 실제 다자 협상·승인 화면은 요구하지 않는다.

재할당의 source·target은 공통 실험 별칭 `S1`, `S2`를 사용한다. 실제 Synchronizer ID는 모델 설정에서 연결한다.

재할당할 계약 집합은 해당 묶음의 후속 사용에 필요한 계약과 의존성으로 결정하고 로그에 남긴다. 계약을 하나로 표현하도록 강제하지 않는다.

### 5.3 업무 버전

정상 경로의 공통 업무 버전은 다음과 같다.

| 버전 | 업무 상태 |
|---|---|
| 0 | 초기 A은행 사용 가능 |
| 1 | Repo 확정, B은행 사용 가능 |
| 2 | 증권대차 확정, C은행 CCP 제공 가능 |
| 3 | CCP 배정·잠금 확정 |

- 확정 성공한 업무 전이만 버전을 증가시킨다.
- 거부·조회·재전송은 버전을 증가시키지 않는다.
- 재할당 성공은 업무 버전을 변경하지 않는다.

## 6. 공통 응답과 멱등성

### 6.1 결과 형식

```json
{
  "run_id": "run-001",
  "request_id": "request-loan-001",
  "actor": "BANK_B",
  "command_type": "CONFIRM_LOAN",
  "outcome": "COMMITTED",
  "replayed": false,
  "effect": {
    "bundle_id": "bundle-001",
    "version_before": 1,
    "version_after": 2,
    "record_type": "LOAN",
    "record_id": "loan-001"
  },
  "error": null
}
```

| `outcome` | 의미 |
|---|---|
| `PENDING` | 진행 중이며 최종 결과가 없음 |
| `COMMITTED` | 업무 효과가 확정됨 |
| `REJECTED` | 해당 요청이 확정적으로 거부됨 |
| `UNKNOWN` | 응답 지연·통신 문제 등으로 관측자가 최종 결과를 확인하지 못함 |

- `effect`는 `COMMITTED`일 때 제공한다.
- `REJECTED`는 공통 오류 코드를 제공한다.
- `PENDING`, `UNKNOWN`의 업무 효과를 추측해서 채우지 않는다.
- `UNKNOWN`은 관측 결과이며, 실제 거래는 이미 확정됐을 수 있다.
- 재할당 성공은 전후 업무 버전이 같고, 효과에 source·target 별칭을 기록한다.
- 명령 응답은 그 요청의 효과다. 이후 거래가 진행된 현재 상태는 별도 조회한다.

### 6.2 제출과 결과 확인

- 제출 호출은 정해진 응답 대기 한도 안에 최종 결과를 알면 반환한다.
- 접수됐지만 처리 중이면 `PENDING`을 반환할 수 있다.
- 응답 대기 한도는 모든 모델에 동일하게 적용하며 실험 조건에서 확정한다.
- 클라이언트가 타임아웃을 경험하면 원래 요청을 `UNKNOWN`으로 관측하고 결과 조회·안전한 재전송으로 확인한다.
- 제출 성공·접수 성공을 거래 확정 성공으로 기록하지 않는다.

### 6.3 멱등성 규칙

멱등성은 원래 제출한 플랫폼에서 `(run_id, 인증된 actor, request_id)`를 기준으로 관리한다. 같은 실행에서 플랫폼을 바꿔 요청 식별자를 재사용하지 않는다.

검증 순서는 다음 원칙을 따른다.

1. 요청 형식과 인증·요청 접근 권한을 확인한다.
2. 같은 요청 식별자의 기존 처리 여부를 확인한다.
3. 동일 업무 내용이면 기존 요청의 결과를 반환하거나 추적한다.
4. 다른 업무 내용이면 요청 식별자 충돌로 거부한다.
5. 신규 요청이면 업무 버전·권한·계약 조건을 검증하고 처리한다.

**기존 요청 조회보다 현재 버전 검사를 먼저 수행하지 않는다.** 버전 1에서 성공한 요청의 재전송이 현재 버전 2라는 이유로 거부돼서는 안 된다.

- 재전송 결과의 `replayed`는 `true`다.
- 같은 요청의 동시 제출도 최대 한 번의 업무 효과만 발생시킨다.
- 새 `request_id`로 이미 사용된 권리를 다시 제출하면 새 요청으로 검증하여 거부한다.
- 멱등성 기록은 해당 실험 실행과 복구 확인이 끝날 때까지 유지한다.

## 7. 후속 거래 준비 상태 조회

Y·Z의 readiness 조회는 다음 정보를 받는다.

- `command_type`
- `bundle_id`
- 해당 업무의 `agreement_id` 또는 `margin_call_id`
- 인증된 요청 주체

응답 예시:

```json
{
  "run_id": "run-001",
  "platform": "Y",
  "bundle_id": "bundle-001",
  "command_type": "CONFIRM_LOAN",
  "ready": true,
  "observed_version": 1,
  "blocking_reasons": []
}
```

`ready=true`는 아래 조건을 확인했다는 의미다.

- 선행 거래 확정
- 현재 사용 권리의 유효성과 필요한 가시성
- 계약상 후속 사용 허용
- 사전 합의·대차 담보 등 업무 전제 충족
- 제출 권한 충족
- B2에서 필요한 계약의 S2 사용 가능

readiness는 조회만 수행한다. 권리를 예약·소진하거나 거래를 자동 확정하지 않는다.

`ready=true` 이후 다른 요청이 먼저 사용하면 실제 제출은 거부될 수 있다. 따라서 제출 시 최신 상태를 재검증한다.

권위 있는 상태를 확인할 수 없으면 `ready=true`로 추정하지 않는다. 통신 오류는 별도 오류로 구분하며, 업무상 사용 불가와 동일하게 취급하지 않는다.

조회 주기·전송 시간·관측 시점이 측정에 미치는 영향은 `measurement.md`에서 동일 기준으로 정한다.

## 8. 공통 상태 조회와 정규화 결과

### 8.1 관측 범위

각 플랫폼의 snapshot은 자신이 확인할 수 있는 업무 기록을 반환한다.

- `run_id`, `platform`
- 국채 묶음 정보
- 권리 기록
- 거래 계약 기록
- 의무 기록
- CCP 배정·증거금 요구 기록
- 남아 있는 예약·처리 상태

빈 목록은 빈 배열로 반환한다. 동일한 논리 기록이 여러 플랫폼에 보이면 같은 공통 식별자로 연결한다. 복제본 여러 개를 별도 권리 여러 개로 계산하지 않는다.

관측기는 각 플랫폼의 최신성·진행 상태를 함께 확인해야 한다. 순차적으로 수집한 snapshot을 하나의 원자적 시점의 상태라고 가정하지 않는다.

최종 정합성 검증은 관련 요청과 복구 처리가 끝난 뒤 수행한다. 경합 중 일시적 이중 사용은 최종 snapshot만으로 부재를 증명하지 않고 거래·권리 이력과 함께 검사한다.

### 8.2 정규화할 핵심 항목

| 기록 | 핵심 필드 |
|---|---|
| 묶음 | `bundle_id`, `security_id`, 수량·단위, 기준 평가액·통화, 확인한 업무 버전 |
| 사용 권리 | 공통 권리 식별자, `bundle_id`, 권리자, 생성 버전, 상태, 허용 업무, 선행 권리 참조 |
| 계약 | 공통 거래 식별자, 유형, 합의 참조, 당사자, 묶음 참조, 업무상 계약 상태 |
| 의무 | `obligation_id`, 유형, 의무자, 권리자, 대상 또는 조건 참조, 계약 참조, 상태 |
| CCP 배정 | `allocation_id`, `margin_call_id`, `bundle_id`, C은행·CCP, 잠금 상태 |
| 증거금 요구 | `margin_call_id`, C은행·CCP, 충족 여부 |
| 진행 상태 | 관련 요청·묶음, 처리 단계, 사용 제한 여부 |

권리 상태는 다음으로 구분한다.

- `AVAILABLE`: 허용된 후속 업무에 사용 가능
- `CONSUMED`: 후속 거래로 이전 권리 소진
- `LOCKED`: CCP 배정으로 추가 사용 금지

일시적 예약·재할당 때문에 사용할 수 없는 경우는 진행 상태로 함께 표현한다. 권리 상태만 보고 사용 가능하다고 판단하지 않는다.

계약의 업무상 유효 상태와 내부 DB 행·Daml 계약의 활성 여부를 구분한다. 내부 계약이 교체돼도 경제적으로 유효한 Repo·증권대차와 의무는 계속 조회돼야 한다.

의무에는 최소한 다음 관계를 구분해 기록한다.

- A은행 → B은행: Repo 환매대금 지급 관련 의무
- B은행 → A은행: Repo 동등증권 반환 관련 의무
- C은행 → B은행: 증권대차 동등증권 반환 의무
- B은행 → C은행: 별도 대차 담보의 반환·해제 관련 의무

금액 산정·실제 반환은 실행하지 않는다. 필요한 대상·조건은 사전 합의를 참조하고, 이번 정상 경로에서는 관련 의무를 미이행 상태로 유지한다.

실제 JSON 구조와 공통 권리·의무 식별자의 생성 규칙은 이 명세 승인 후 JSON Schema와 fixture에서 구체화한다.

## 9. 공통 오류 분류

아래는 업무상 의미다. 내부 오류 문구·예외 이름을 그대로 비교하지 않는다.

| 코드 | 의미 |
|---|---|
| `INVALID_REQUEST` | 필수 값·자료형·명령·제공 플랫폼 등이 잘못됨 |
| `UNAUTHENTICATED` | 요청 자격을 확인할 수 없음 |
| `FORBIDDEN` | 인증된 주체에게 해당 명령·조회 권한이 없음 |
| `NOT_FOUND` | 조회 대상 실행·요청·업무 기록이 존재하지 않음. 원래 거래의 확정 실패를 의미하지 않음 |
| `PRECONDITION_NOT_MET` | 선행 확정·합의·대차 담보 제공 등 전제 미충족 |
| `REQUEST_ID_CONFLICT` | 같은 요청 식별자에 다른 업무 내용 사용 |
| `VERSION_CONFLICT` | 요청이 근거로 삼은 업무 버전과 현재 버전이 다름 |
| `USE_NOT_PERMITTED` | 재사용 또는 CCP 후속 제공이 허용되지 않음 |
| `RIGHT_UNAVAILABLE` | 권리가 이미 사용·잠금됐거나 현재 확보할 수 없음 |
| `COLLATERAL_NOT_ELIGIBLE` | 모사된 CCP 적격성·수락 조건 미충족 |
| `TEMPORARILY_UNAVAILABLE` | 내부 상태나 연결 문제로 처리를 진행·확인할 수 없음 |
| `OUTCOME_UNKNOWN` | 요청의 실제 확정 결과를 현재 확인할 수 없음 |
| `INTERNAL_ERROR` | 그 밖의 예상하지 못한 구현 오류 |

업무상 거부는 `REJECTED`와 오류 코드로 반환한다.

일시적 연결 실패·내부 오류를 근거 없이 확정 거부로 바꾸지 않는다. 업무 효과 발생 여부를 모르면 `UNKNOWN`으로 추적한다.

형식·인증 오류처럼 명령 접수 전에 발생한 오류는 공통 오류 객체로 반환한다. 이때 기존에 같은 식별자의 요청이 있었다면 그 요청의 결과를 덮어쓰지 않는다.

동시에 여러 조건이 맞지 않을 수 있는 경합에서는 `VERSION_CONFLICT`와 `RIGHT_UNAVAILABLE` 등 동등한 거부 사유가 발생할 수 있다. 허용 코드 집합은 각 acceptance 케이스에 명시한다.

## 10. 인증과 실험 관측 권한

로컬 PoC에서 전체 사용자 관리·로그인 화면은 구현하지 않는다.

- 실행 설정에 등록한 기관별 로컬 자격 정보를 사용한다.
- 자격 정보와 기관의 연결은 서버 측에서 검증한다.
- 플랫폼별 업무 권한을 확인한다.
- 실험 관측기에는 별도의 읽기 권한을 부여한다.
- 권한 없는 요청자는 다른 기관의 요청 결과나 전체 snapshot을 조회할 수 없다.
- 토큰·비밀값은 저장소·fixture·실험 로그에 포함하지 않는다.
- HTTP 서비스는 기본적으로 로컬 환경에 한정한다.

Canton에서는 인증된 업무 주체를 설정된 Party·제출 권한에 연결한다. DB/API에서도 동일한 업무상 권한 제한을 적용한다.

이 설정은 공통 업무 권한 검증을 위한 최소 범위이며, 상용 인증·보안 수준이나 프라이버시 보장 전체를 평가한 것으로 해석하지 않는다.

## 11. 계측·구현 중립성

- 요청·결과·상태 이력은 `run_id`, `request_id`, `bundle_id`와 거래 식별자로 연결한다.
- 실제 거래 확정, 응답 수신, 로컬 반영, 후속 준비 완료를 별도 이벤트로 기록한다.
- 응답 본문의 시각 하나로 모든 시간 지표를 계산하지 않는다.
- 공통 API의 HTTP 응답시간과 Phase 4의 업무 시간 지표를 동일시하지 않는다.
- 자동 제출·조회 조건과 타임스탬프 정의는 `measurement.md`에서 고정한다.
- A의 내부 API·이벤트와 B의 원장 제출·확정·재할당을 각각 기록한다.
- API 수와 Daml 인터페이스 수는 유형별로 집계한다.
- 특정 내부 처리 단계·DB 기술·Daml 계약 개수를 강제하지 않는다.

## 12. 후속 산출물

이 명세 승인 후 다음을 구체화한다.

- `shared/schemas/`: 명령·결과·readiness·snapshot·fixture 스키마
- `shared/fixtures/`: 정상·권한 거부·재사용 불허·담보 조건 미충족·중복·경합 데이터
- `spec/acceptance.md`: 입력, 실행 순서, 허용 결과와 최종 상태
- `spec/measurement.md`: 이벤트, 관측 지점, 반복·대기·재시도 조건

구현별 언어·프레임워크·DB·Canton 버전과 실행 방법은 이후 각 구현 폴더의 README에 작성한다.

## 13. 공통 JSON 형식

연구 총괄이 승인한 구체적인 데이터 계약과 예시는 [shared/README.md](../shared/README.md), [공통 Schema](../shared/schemas/), [테스트 데이터](../shared/fixtures/)에 반영한다.

- 식별자는 1~128자의 영문·숫자·`-`·`_`·`.`·`:` 문자열이다.
- 이번 수량 단위는 `KRW_FACE_VALUE`, 통화는 `KRW`다. 자산 수량은 양수의 정수 문자열, 금액은 음수가 아닌 정수 문자열로 표현한다.
- 정상 fixture의 액면·평가액은 각각 100억 원으로 고정한 테스트 가정이다. 실제 국채 가격을 일반화하지 않는다.
- 권리 ID는 `{bundle_id}:right:0`, `:right:1`, `:right:2`이며 CCP 배정은 같은 C은행 논리 권리를 LOCKED로 바꾼다.
- 의무 ID·대상 형식·기대 결과 비교 규칙은 shared 문서와 Schema를 따른다.
- 접수 전·조회 오류는 `run_id`, `request_id`, `error` 형식이며 해석 불가 ID는 null이다.
- HTTP 상태는 확정 결과 200, 접수 후 PENDING 202, 형식·플랫폼 오류 400, 인증 실패 401, 권한 부족 403, 조회 대상 미존재 404, 요청 ID 내용 충돌 409, 현재 처리·결과 확인 불가 503으로 구분한다.
- 409 응답은 기존 요청의 원래 결과를 덮어쓰지 않는다. 404 NOT_FOUND도 원래 거래의 확정 실패를 의미하지 않는다.
- snapshot_seq는 플랫폼·실행별 응답 순번이며 최신성 보증이 아니다.
- Schema는 형식 검증이다. 권한·참조·이중 사용·복구 검증은 업무 구현과 공통 검증기에서 수행한다.
